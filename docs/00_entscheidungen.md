# Entscheidungen, Annahmen, offene Punkte

Stand: 2026-10-07, Revision 4 mit Festlegungen für M0 (E34–E55; vorherige Stände unter `_archiv/`)

| E55 | Format der API-Vektoren | Ein Vektor ruft genau eine `Board`- oder `Move`-Funktion: `function`, `args`, bei Methoden `board` (FEN plus Züge) oder `move`, dazu `result`, `result_contains` oder `error`; verändernde Funktionen nennen `board_after`, auch nach einem Fehler. Werte: Ganzzahlen im Bereich ihres Grundtyps, `u64` und `Bitboard` als `0x` plus 16 Hexziffern, `Board` als FEN, Listen als Arrays, `unordered` für Zuglisten. Jede `Board`- und `Move`-Funktion hat einen erfolgreichen Vektor und einen je deklariertem Fehler; `id` ist dateiübergreifend eindeutig und beginnt mit dem Dateipfad | `spec-check` erzwingt Abdeckung, Argumentzahl und Typen; kein Vektor nutzt einen Wert außerhalb des Typbereichs oder einen `Move` mit den unbenutzten Flags 6/7. `Clock`, `Log`, `Bot`, `run` und `load_data` testet jedes Binding selbst. | E64 | Wheels des Python-SDK | cibuildwheel 4.3 im Workflow `wheels.yml` auf nativen Runnern: Windows x64, Linux x64 und arm64 (`manylinux_2_28`), macOS x64 und arm64 (ab macOS 11); CPython 3.11 bis 3.14 ohne free-threaded und ohne musllinux. | E65 | Ort und Regeln des Referee-Kerns | Der Referee-Kern liegt im Python-SDK-Paket als `sbm.referee`, die lokale Arena als `sbm.arena` mit dem Befehl `sbm-arena`; der Runner auf dem Server importiert dasselbe Paket. Der Referee kennt nur die Schnittstelle `Player` (starten, senden, empfangen mit Frist, einfrieren, fortsetzen, beenden). Ablauf: Bots starten nacheinander (Weiß, dann Schwarz), jeder mit eigenem Startbudget; wer es überschreitet, wird sofort eingefroren. Je Zug: fortsetzen, auf vorzeitig gesendete Zeile prüfen (`unexpected_message`), `turn` senden, Antwort mit Frist Restzeit + Toleranz lesen, einfrieren, prüfen. Die Toleranz gilt nur für Züge, nicht für den Start. Zug-Fehler: Schema-Verstoß ergibt `protocol_violation`, ein im Kern nicht legaler Zug `illegal_move`; der Bot bekommt vorher `error`. Wer abstürzt oder auf Zeit verliert, bekommt kein `game_over` mehr. `max_moves` zählt ganze Züge (Standard 500). Ohne Uhr (`clock=False`) gelten keine Fristen und es wird keine Zeit abgezogen. Zeitüberschreitung schlägt jeden anderen Fehler desselben Zuges | Ein `pip install` genügt für Bot und Arena; keine zweite Implementierung für den Server. Nacheinander starten hält die Fairness auf einem Kern (E12). Standardwerte der lokalen Einstellungen: Toleranz 20 ms, Startbudget 10 s, Speicher 1024 MiB; auf dem Server kommen alle Werte aus der Disziplin. Ausnahmen außerhalb der Spieler-Fehler sind Infrastrukturfehler: Das Spiel wird verworfen, beide Spieler werden beendet |
| E66 | Prüfung der Bot-Nachrichten | Handgeschriebene strenge Prüfung in `sbm.referee.bot_messages` statt eines JSON-Schema-Validators zur Laufzeit; das Paket bleibt ohne Abhängigkeiten. Sie übernimmt die Semantik von JSON Schema: `1.0` ist eine Ganzzahl, `true` nicht; Muster ohne abschließenden Zeilenumbruch. `NaN` und `Infinity` sind ungültiges JSON. Zu tief verschachtelte Nachrichten und Ganzzahlen mit mehr als 64 Ziffern gelten als Schema-Verstoß. `v` ≠ 1 in `ready` ergibt den Fehlercode `unsupported_version` | Die Tests vergleichen das Urteil mit `jsonschema` über alle Beispielnachrichten und eine Liste von Grenzfällen; weichen sie ab, ist die Prüfung falsch, nicht das Schema. Der Python-Parser würde bei tiefer Verschachtelung mit `RecursionError` und bei sehr langen Zahlen mit `ValueError` scheitern; beides darf den Referee nicht beenden |
| E67 | Bedienung und Verhalten der lokalen Arena | Aufruf `sbm-arena WEISS SCHWARZ [Optionen]` (auch `python -m sbm.arena`), ohne Konfigurationsdatei. Ein Bot ist eine `.py`-Datei (läuft mit dem Python der Arena), eine andere Programmdatei, eine Befehlszeile (`"java -jar bot.jar"`) oder `tcp[:PORT]` (Standard 7470) für einen in der IDE gestarteten Bot. Optionen: `--games` (Farben wechseln), `--time` (Sekunden plus Inkrement, Standard `60+1`), `--no-clock`, `--fen`, `--pgn` (hängt an), `--moves`, `--quiet`, `--startup-ms`, `--tolerance-ms`, `--max-moves`. Lokale Bots werden außerhalb des eigenen Zuges eingefroren, samt aller Kindprozesse: unter Linux und macOS eigene Sitzung und `SIGSTOP`/`SIGCONT` an die Prozessgruppe, unter Windows ein Job-Objekt plus Suche nach Nachkommen über die Elternprozess-Kennung (der Python-Starter einer venv legt den eigentlichen Interpreter außerhalb des Jobs an). Scheitert das Einfrieren, läuft der Bot mit einer Warnung uneingefroren weiter. TCP-Bots werden nie eingefroren; sie verbinden sich vor dem Start der Partie, die Wartezeit zählt nicht zum Startbudget, je Partie eine neue Verbindung. Nach der Partie hat ein Bot 2 s, um sich selbst zu beenden; danach werden er und alle Nachkommen beendet. PGN: `Termination` als Standardwert (`time forfeit`, `rules infraction`, `abandoned`, `adjudication`, `unterminated`, sonst `normal`), der genaue Code im Schlusskommentar. Exit-Codes: 0 fertig, 1 Fehler der Arena, 2 falsche Argumente, 130 abgebrochen. Ein menschlicher Spieler auf der Konsole kommt später; Speicher wird lokal nicht begrenzt (O17) | Positionsargumente halten den häufigsten Aufruf kurz. Einfrieren wie auf dem Server macht lokale Zeitmessungen vergleichbar und deckt Bots auf, die sich auf Rechnen in gegnerischer Zeit verlassen. Eigene Sitzung bzw. Prozessgruppe sorgt dafür, dass Strg+C nur die Arena trifft und diese die Bots geordnet beendet |
| E68 | Referenzbots für Python | Zwei Bots im SDK-Paket unter `sbm.bots`: `random_mover` (gleichverteilt unter den legalen Zügen) und `material` (Alpha-Beta-Negamax über 2 Halbzüge, Bewertung nur nach Material mit 100/300/300/500/900, Matt als ±100000 abzüglich Entfernung, Remis 0; unter gleich bewerteten Zügen zufällig; meldet `depth`, `score_cp` bzw. `score_mate` und `nodes` per `info`). Start mit `python -m sbm.bots.<modul>`; in der Arena genügen die Kurznamen `random` und `material` (ohne Beachtung der Groß-/Kleinschreibung). Sie haben Vorrang vor einem Befehl gleichen Namens; eine Datei dieses Namens wird als Pfad angegeben (`./random`) | Gegner ohne eigenen Code, sobald das Paket installiert ist, und kurze Vorlagen für den Aufbau eines Bots. ## 4. Risiken

| ID | Risiko | Einordnung |
|----|--------|-----------|
| R2 | Verhalten weicht zwischen Sprachen ab | Durch E3 stark reduziert: Regeln liegen nur im Kern. Verbleibend: Fehler in den Bindings → Binding-Tests je Sprache |
| R3 | Statische Analyse ist umgehbar | Bleibt als zweite Schicht Pflicht, darf aber nie die einzige sein |
| R4 | Der Runner läuft als Container mit erweiterten Rechten und führt auch die Verifikation aus (E81); ein Fehler dort wirkt wie Root auf dem Host | Nicht im Netz `local-web`, nicht von außen erreichbar, Aufträge nur über die DB |
| R11 | Build auf dem schwachen Server (C++-Kern, Frontend, fünf Laufzeiten) dauert und belastet andere Dienste | Queue beim Deploy pausieren; Ausweichmöglichkeit: Images in GitHub Actions vorbauen |
| R5 | Rechenbedarf langer Partien auf schwacher Hardware | Alles konfigurierbar (E13), Queue nutzt die Zeit lückenlos (E20), Laufzeitschätzung in der Admin-UI |
| R6 | Wanduhrzeit auf geteiltem Server: Fremdlast kostet den Bot am Zug Bedenkzeit | Akzeptiert (E12, E19); gedämpft durch festen Kern und CPU-Priorität |
| R7 | Übergang über die Sprachgrenze kostet pro Aufruf Zeit | Grobkörnige API (ganze Zuglisten, Massenabfragen), siehe [sdk-api.md](komponenten/sdk-api.md) |
| R8 | Vorkompilierte SDK-Pakete müssen für jede Plattform der Entwickler gebaut werden | Build-Matrix in CI (Windows, Linux, macOS); für Python (E64) und C# (E199, E200) umgesetzt |
| R9 | Debugger der Bot-Sprache kann nicht in den Kern steppen | Kern liefert aussagekräftige Fehler; Brettzustand jederzeit als FEN/Text ausgebbar |
| R10 | Gäste können Spiele gegen Bots starten (E11) und damit die Queue belasten | Eigene Kapazitätsgrenze, niedrigste Priorität |
